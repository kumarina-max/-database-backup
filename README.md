## Задание 1

### 1.1. Восстановление за предыдущий день
– Ежедневное полное резервное копирование (Full Backup) – простой и быстрый вариант, но требует много места.
– Дифференциальное копирование – экономнее: еженедельный полный бэкап + ежедневные дифференциальные (только изменения с момента полного). Восстановление: полный + последний дифференциальный.

### 1.2. Восстановление за час до сбоя
– Точечное восстановление (Point-in-Time Recovery) – комбинация полных/инкрементных бэкапов и непрерывного архивирования журналов транзакций (WAL, binary logs).
– Делаются инкрементные копии или архивируются логи каждые 15–30 минут. При восстановлении: необходимо развернуть последнюю полную копию, затем накатить все журналы до нужного момента.

### 1.3. Моментальное переключение на работающую БД
– Да, реализуется через репликацию (Master‑Slave) с синхронной или асинхронной передачей изменений и автоматическим переключением (failover) (например, Patroni, Galera, AlwaysOn, облачные Multi‑AZ).
– При сбое основной ноды резервная становится активной за секунды/минуты, обеспечивая почти нулевое время простоя.

## Задание 2

### 2.1. Команды резервирования и восстановления (pg_dump / pg_restore)

Резервирование (формат custom – сжатый, гибкий):
pg_dump -Fc -h host -p port -U user -d dbname > backup.dump

Восстановление (с очисткой перед вставкой):
pg_restore -h host -p port -U user -d dbname -c backup.dump


### 2.1. Автоматизация
Да, возможна:

- Скрипт + Cron – создаётся shell-скрипт с вызовом pg_dump и добавлением даты в имя, удалением старых бэкапов и загрузкой в облако. Запуск по расписанию (например, ежедневно в 3:00).

- Готовые инструменты – pg_back, barman, а также встроенные механизмы облачных провайдеров (AWS RDS, GCP Cloud SQL) с автоматическим бэкапом и настраиваемым сроком хранения.

## Задание 3

### 3.1. Пример команды инкрементного резервного копирования MySQL

Инкрементное резервное копирование в MySQL выполняется с помощью коммерческого инструмента MySQL Enterprise Backup (mysqlbackup). Базовая команда:

''' bash
mysqlbackup --backup-dir=/path/to/backup --incremental \
--incremental-backup-dir=/path/to/incremental backup
--incremental — указывает на создание инкрементной копии.

--incremental-backup-dir — каталог для хранения инкрементного бэкапа.
'''

Также требуется указать базу для сравнения через --incremental-base или --start-lsn.

Альтернативный подход (бесплатный) — использование бинарных логов:

Периодически выполнять полный бэкап (например, mysqldump).

Регулярно создавать новые бинарные логи командой FLUSH LOGS или mysqladmin flush-logs.

При восстановлении сначала развернуть полную копию, затем применить нужные бинарные логи через mysqlbinlog.

### 3.1.* Преимущества реплики перед обычным резервным копированием

- Репликация не заменяет резервное копирование, но даёт важные преимущества:

- Высокая доступность — при сбое основной ноды реплика может взять нагрузку на себя за секунды.

- Разгрузка основной БД — бэкап можно делать с реплики, не останавливая и не нагружая мастер.

- Распределение нагрузки — запросы на чтение можно направлять на реплики.

- Минимальный RPO (Recovery Point Objective) — реплика содержит изменения почти в реальном времени, в отличие от бэкапа, который делается по расписанию.

Важно: реплика не защищает от логических ошибок (случайное удаление, коррупция данных) — для этого нужны бэкапы. Репликация и бэкапы дополняют друг друга.
